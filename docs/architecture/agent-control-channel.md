# Agent Control Channel

## Status

Canonical Pantheon worker/control trust-boundary specification.

## Purpose

Pantheon needs a secure path by which an executing worker can request canonical actions, seal artifacts, spawn bounded work, and submit results without inheriting operator authority.

The central rule is:

> **An Attempt credential authenticates which Attempt is calling Pantheon. It grants no authority. The Agent Control surface exposes only worker operations, and every consequential operation is independently validated against current Pantheon state and authorization policy.**

This document defines the logical worker-facing control protocol. Concrete ExecutorBackends may expose that protocol as HTTP, native structured tools, MCP-style calls, function calls, or adapter mediation. Pantheon core depends only on the canonical semantics.

## 1. Operator Control and Agent Control are different surfaces

Pantheon has two logical control surfaces:

```text
                     pantheond
                        │
          ┌─────────────┴─────────────┐
          │                           │
          ▼                           ▼
   OPERATOR CONTROL              AGENT CONTROL
      SURFACE                      SURFACE
          │                           │
          ▼                           ▼
 human / CLI / UI              Attempt workload
 operator authority            Attempt identity
```

The existing public `/api/v1` contract is the operator-facing control surface.

The Agent Control surface is a separate route set and principal class. It never exposes operator operations such as:

- approving grants;
- raising budgets;
- revising policy;
- forcing recovery resolution;
- enabling/draining backends;
- integrating shared Git refs;
- cancelling unrelated Goals/Tasks;
- reading arbitrary Artifacts or other Tasks' state.

Possession of a valid Agent Control credential does not allow an Agent to reach operator handlers.

## 2. Separate socket paths alone are not a security boundary

On a local single-user system, the daemon and a worker may run under the same operating-system user. Therefore Unix-socket filesystem ownership or peer UID alone cannot distinguish an operator from an untrusted worker.

Pantheon requires both:

1. **logical surface separation** — operator and worker operations use distinct route sets/principals; and
2. **physical reachability isolation** — the operator control endpoint and control-plane storage are not reachable from an untrusted execution sandbox.

The operator endpoint must never be mounted/exposed into an untrusted worker environment.

## 3. Agent Control identity belongs to Attempt

Identity is scoped to the concrete execution lineage:

```text
Logical Agent
     │
Task
     │
Run
     │
Attempt
     │
AgentControlSession
```

Every Attempt receives a distinct AgentControlSession.

A new Attempt under the same Run receives a new session because it represents a new backend execution lineage.

A daemon or adapter restart that recovers the same Attempt does **not** create a new session.

## 4. AgentControlSession creation

AgentControlSession is created durably in the same transaction that creates the Attempt and immutable LaunchKey.

Conceptually:

```text
LaunchReady=True
      ↓
BEGIN
  create Attempt
  assign LaunchKey
  create AgentControlSession
  persist credential verifier
COMMIT
      ↓
make Agent Control identity/channel available to execution
      ↓
ensureExecution(...)
```

Conceptual record:

```yaml
agentControlSession:
  id: acs_123
  attempt: attempt_456
  state: ACTIVE
  credentialVerifier: sha256:...
  createdAt: ...
```

Run, Task, Goal, Agent, Binding, and policy context are derived from the Attempt relationship. They are not caller-controlled identity claims.

## 5. V1 credential

V1 uses a high-entropy opaque random credential generated by Pantheon for the AgentControlSession.

Requirements:

- cryptographically random;
- at least 256 bits of entropy;
- raw credential shown only to the corresponding Attempt execution path;
- only a one-way verifier/hash is persisted;
- never logged or emitted in Events;
- never stored in Artifact metadata, Run snapshots, backend attachments, or diagnostic payloads.

The credential audience is only the Pantheon Agent Control gateway.

Pantheon does not need JWT, certificates, SPIFFE, or a local PKI for the local-first v1.

## 6. Credential delivery

The preferred integration makes the credential available to the execution mechanism without placing it in model context.

Possible implementations include:

- a sandbox-local read-only credential file;
- an inherited protected file descriptor;
- adapter-mediated calls where the model never sees the credential;
- backend-native structured tool mediation.

Avoid exposing the credential through:

- prompts;
- command-line arguments;
- public environment dumps;
- Events/logs;
- Artifacts;
- shell history.

A non-secret endpoint/tool description may be injected separately.

## 7. Authentication is not authorization

A valid Agent Control credential proves only:

> This request originates from AgentControlSession X for Attempt Y.

It does **not** prove that the Attempt may perform the requested operation.

The flow is:

```text
worker request
      ↓
Agent Control gateway
      ↓
authenticate AgentControlSession
      ↓
derive Attempt / Run / Task / Agent / Goal
      ↓
validate current lifecycle/state preconditions
      ↓
normalize canonical operation
      ↓
current Policy Decision Point
      ↓
PERMIT / DENY
      ↓
controller or privileged broker
```

The Agent cannot self-declare another Task, Run, Agent, Goal, or principal.

## 8. Agent Control session lifecycle

V1 session states are intentionally small:

```text
ACTIVE
  ↓
REVOKED
```

A session is revoked when its Attempt can no longer exercise worker authority, including:

- Attempt terminalization;
- Run/Task cancellation that revokes worker execution authority;
- forced recovery/tombstoning;
- explicit security revocation of that execution lineage.

Policy tightening does not necessarily revoke identity. The Attempt may remain authenticated while new operations are denied under the current policy.

Late requests from a revoked session cannot mutate authoritative state.

## 9. Recovery continuity

Daemon restart or adapter restart does not rotate AgentControlSession identity when the same Attempt may still be alive.

```text
same Attempt
same LaunchKey
same AgentControlSession
```

This matches Pantheon's rule that reconciliation of one execution lineage is not a retry.

A fresh Attempt gets:

```text
new Attempt ID
new LaunchKey
new AgentControlSession
new credential
```

## 10. Logical protocol is transport-neutral

Pantheon defines Agent Control as semantic operations, not one required wire protocol.

```text
Canonical Agent Control Operations
                │
        ┌───────┼─────────┐
        ▼       ▼         ▼
   local HTTP   native     adapter
   gateway      tools      mediation
```

A backend may expose canonical operations as native function/tool calls. Another may use a sandbox-local HTTP client. Another may translate a native final response into `task.submit_result` through its adapter.

Pantheon core must not branch on the concrete transport/harness.

## 11. V1 operation surface

Initial worker operations should be deliberately small:

```text
session.describe
request.get

action.invoke
artifact.seal

task.spawn
task.graph.propose

task.submit_result
```

Optional non-authoritative progress reporting may be added without expanding authority.

The Agent Control surface does not expose generic operator resource reads or arbitrary `/api/v1/*` routes.

## 12. Agent request idempotency

Every consequential worker request has an Attempt-scoped `requestId`.

Canonical identity:

```text
(attemptId, requestId)
```

Pantheon persists the canonical request hash and outcome state.

Rules:

```text
new requestId
→ process request

same requestId + same canonical request hash
→ return/reconcile the existing request

same requestId + different canonical request hash
→ fail closed as request identity misuse
```

This generalizes the existing dynamic-spawn duplicate-prevention rule to every worker/control operation.

## 13. Durable agent request record

Conceptually:

```yaml
agentRequest:
  attempt: attempt_456
  requestId: req_01K...
  requestHash: sha256:...
  operation: action.invoke
  state: PENDING
  resultRef: null
  problemRef: null
```

For requests whose brokered operation may have an external side effect, status may include:

```text
PENDING
STARTED
SUCCEEDED
FAILED
UNKNOWN
```

A crash or lost response after a possible external side effect must not cause blind duplicate execution.

## 14. `action.invoke`

`action.invoke` is the worker-facing entry to the canonical authorization/broker pipeline.

Conceptual request:

```yaml
requestId: req_01K...
action:
  name: git.push
resource:
  ref: repo://Pantheon/origin/main
arguments: ...
```

Pantheon derives the principal and enclosing context from the AgentControlSession.

The Agent never constructs or issues its own Capability Ticket.

Flow:

```text
request
  ↓
canonical normalization
  ↓
current PDP
  ↓
DENY
or
PERMIT
  ↓
exact-operation authorization
  ↓
Execution/privileged Broker
```

## 15. Approval flow

When an operation is denied as approvable:

```text
Agent request
   ↓
DENY / approval-required
   ↓
ApprovalRequest
```

The Agent may observe that approval is pending, but it cannot approve it.

Only an authorized operator surface may create the scoped human Grant.

After approval, Pantheon re-evaluates the exact operation under current policy and Grant state.

Authorization remains binary PERMIT/DENY.

## 16. `artifact.seal`

The worker may request that content from its own authorized workspace/output surface be sealed.

Pantheon derives the caller's Task workspace and validates the source path/resource itself.

The worker cannot use `artifact.seal` to read/seal arbitrary host paths, control-plane state, another Task's workspace, or inaccessible Artifact content.

Pantheon computes/verifies all digests itself and follows the Artifact/CAS durability protocol.

## 17. `task.spawn` and `task.graph.propose`

The worker supplies desired bounded outcomes, declared inputs/outputs, relationship semantics, reason, and request identity.

Pantheon derives:

- parent Attempt;
- parent Run;
- parent Task;
- Goal;
- ancestry/security ceilings.

Caller-supplied parent identity is never authoritative.

The Graph Controller remains the only component that materializes Tasks or mutates TaskGraph state.

## 18. `task.submit_result`

Candidate submission requires all of the following at commit time:

```text
AgentControlSession == ACTIVE
Attempt is current nonterminal Attempt of Run
Run.phase == Active
Task.phase == Active
Run is current responsible Run for Task
expected Task status revision matches
no cancellation/finalization fence has already committed
```

The submission transaction must re-read and CAS these preconditions.

If cancellation/finalization commits first, submission fails closed as a conflict.

> **Cancellation wins a race with candidate submission.**

If candidate submission commits first and cancellation arrives afterward, the immutable Candidate remains historical truth, but the Task may still be cancelled according to lifecycle policy.

## 19. Native execution is not automatically a security boundary

A same-user host-native worker with arbitrary shell/filesystem access cannot be considered strongly isolated merely because the Agent and operator endpoints use different Unix socket paths.

Therefore:

```text
native
=
trusted execution mechanism
not a strong isolation boundary
```

Model-driven workers with broad shell/filesystem capability require an execution environment that can enforce control-plane isolation unless an operator explicitly selects an unsafe/trusted override mode.

Pantheon must fail closed when required isolation cannot be enforced.

## 20. Control-plane isolation requirement

Untrusted execution must be unable to directly reach:

- the operator control endpoint;
- `pantheon.db` and WAL/journal state;
- Pantheon CAS/storage internals;
- policy/configuration files;
- Agent Genome/private configuration not intentionally projected;
- other Tasks' workspaces;
- shared Git common-dir authority/ref mutation paths;
- privileged host sockets/credential agents not explicitly brokered.

The Sandbox Broker/Controller owns the concrete enforcement mechanism.

## 21. Execution Fabric integration

Agent Control semantics are normalized execution features, not backend identities.

Examples:

```text
control.result-submit
control.artifact-seal
control.action-invoke
control.task-spawn
control.graph-propose
```

A Task/Agent-specific ExecutionRequest may require those features.

A backend can satisfy them through any adapter-private mechanism.

A backend that cannot provide a required Agent Control semantic is incompatible with that request.

Control-plane isolation is an infrastructure/isolation fact and cannot be self-awarded by a backend quality claim.

## 22. Remote backends

V1 does not expose Agent Control as an unauthenticated public TCP service.

Future remote workers may reach the logical Agent Control gateway through an authenticated adapter/tunnel or future remote workload-identity design.

The local-first v1 does not require distributed workload PKI.

## 23. Security concept separation

Pantheon keeps four different concepts separate:

```text
Agent Control credential
  "I am Attempt X"

Capability Grant
  "trusted authority granted scoped permission"

Capability Ticket / exact-operation authorization
  "Pantheon permitted this exact broker operation"

External Secret
  "credential material used against Git/cloud/etc."
```

An Agent Control credential is never accepted by external services or the operator API.

## 24. Persistence model

V1 persistence needs at least:

```text
agent_control_sessions
──────────────────────
id
attempt_id UNIQUE
credential_hash
state
created_at
revoked_at
revocation_reason
```

and:

```text
agent_requests
──────────────
attempt_id
request_id
request_hash
operation
state
result_ref
problem_ref
created_at
updated_at

PRIMARY KEY(attempt_id, request_id)
```

Raw Agent Control credentials are never persisted.

AgentControlSession creation belongs to the Attempt-creation transaction.

Session revocation belongs to the transaction that conclusively removes worker authority from the Attempt.

## 25. Events and audit

Useful authoritative events include:

```text
pantheon.agent-control.session.created.v1
pantheon.agent-control.session.revoked.v1
pantheon.agent-request.accepted.v1
pantheon.agent-request.denied.v1
```

Do not duplicate every semantic operation with redundant high-volume Agent Control events when the underlying controller already records an authoritative domain event.

Credential material is never logged.

## 26. Core invariants

1. **Operator Control and Agent Control are separate route sets and principal classes.**
2. **Two same-user Unix socket paths alone are not a security boundary.**
3. **The operator endpoint is physically unreachable from untrusted worker sandboxes.**
4. **Agent Control identity is Attempt-scoped.**
5. **AgentControlSession is durably created with the Attempt before backend execution.**
6. **The raw credential is high entropy, scoped to Pantheon Agent Control, and never persisted/logged.**
7. **Authentication establishes identity only; it grants no operation authority.**
8. **Current Task/Run/Attempt/policy state is validated for every consequential operation.**
9. **The Agent Control protocol is semantic/transport-neutral.**
10. **The Agent surface exposes no operator verbs.**
11. **Every consequential worker request is Attempt-scoped and idempotent.**
12. **Ambiguous external side effects reconcile as UNKNOWN rather than being blindly re-executed.**
13. **Spawn/result/action identity is server-derived from the Attempt.**
14. **Candidate submission is revision-bound and cancellation wins races.**
15. **New Attempt means new AgentControlSession; reconciliation of the same Attempt preserves it.**
16. **Same-user native shell execution is not treated as strong isolation.**
17. **Required control-plane isolation failures fail closed.**
18. **Agent Control credentials, Grants, exact-operation authorization, and external Secrets are distinct concepts.**

## v1 scope

Include:

- separate logical operator and Agent Control surfaces;
- Attempt-scoped AgentControlSession;
- opaque high-entropy local credential/verifier;
- transport-neutral worker-operation semantics;
- `action.invoke`;
- `artifact.seal`;
- `task.spawn`;
- `task.graph.propose` where policy allows;
- `task.submit_result`;
- durable Agent request idempotency;
- strict candidate-submission preconditions;
- control-plane isolation requirement;
- execution-feature advertisement for Agent Control semantics.

Defer:

- remote public Agent Control listener;
- mTLS/SPIFFE workload identity;
- distributed Agent Control gateway;
- credential rotation within one short-lived Attempt unless future runtimes require it;
- generic worker access to operator resource APIs;
- rich worker event/watch subscriptions.
